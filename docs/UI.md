# UI

## 목적
- NoWhere의 UI/UX 규칙과 화면 설계 기준을 정의한다.
- 모든 화면은 업무 처리 효율, 명확한 상태 표현, 일관된 조작 방식을 우선한다.
- 새로운 기능을 추가할 때는 본 문서의 디자인 시스템과 UX 원칙을 따른다.

## UI 철학
- NoWhere는 소비자용 감성 UI보다 업무용 운영 UI에 가깝다.
- 디자인의 목표는 예쁨보다 빠른 판단과 빠른 처리다.
- 사용자는 화면을 감상하지 않고, 주문·배차·정산·운영 업무를 수행한다.
- 따라서 모든 화면은 단순하고, 예측 가능하고, 재사용 가능해야 한다.

## 핵심 원칙
- 필요한 정보만 보여준다.
- 같은 기능은 같은 UI 패턴을 사용한다.
- 클릭 수와 입력 수를 최소화한다.
- 시각 효과보다 상태 전달을 우선한다.
- 새 디자인보다 기존 컴포넌트 재사용을 우선한다.
- 한 화면에는 하나의 핵심 목적을 둔다.
- 앞으로 모든 UI 수정은 본 문서를 최우선 기준으로 삼는다.
- AI와 개발자는 사용자의 별도 지시가 없는 한 본 문서의 규칙을 예외 없이 유지해야 한다.
- 화이트 모드와 다크 모드는 서로 다른 감성 UI가 아니라 동일한 미니멀 운영 UI 철학으로 관리한다.

## 디자인 스타일
- Minimal UI
- Flat Design
- Business First
- Professional Dashboard
- Functional Layout

## Color System

### 기본 색상
- Background: `#F3F3F3`
- Surface: `#F7F7F7`
- Layered Surface: `#EFEFEF`
- Primary Text: `#1F1F1F`
- Secondary Text: `#6A6A6A`
- Border: `#DDDDDD`
- Hover: `#EDEDED`
- Disabled: `#CFCFCF`

### 상태 색상
- 기본 상태 표현은 Gray 계열만 사용한다.
- Info, Warning, Danger 색상은 개념상 예약만 해두고 기본 적용하지 않는다.
- 의미 색상은 사용자가 별도로 지정했을 때만 도입한다.

### 색상 원칙
- 색상은 장식이 아니라 상태 표현에 사용한다.
- 브랜드 컬러가 생기기 전까지 과도한 포인트 컬러 사용을 금지한다.
- 동일 상태는 동일 색상 체계를 유지한다.
- 기본 인터랙션 요소는 무채색 체계를 사용한다.
- 버튼, 카드, 입력창은 원칙적으로 포인트 컬러를 사용하지 않는다.
- 강조가 필요해도 `Gray`, `Dark Gray`, `Black` 범위 안에서만 해결한다.
- 사용자가 별도로 색상을 지정하기 전까지는 모든 요소를 그레이스케일로만 구성한다.
- Border, Select, Badge, Error Box, Toast도 기본적으로 무채색 규칙을 따른다.
- 의미 색상은 시스템 기본값으로 두지 않으며, 필요 시 별도 지시를 받은 후 적용한다.
- 다크 모드에서도 동일 원칙을 유지한다.
- 기본 다크 모드는 보더, 텍스트, 간격, 구조로만 요소를 구분한다.
- 사용자가 별도로 요청한 경우 다크 모드에 한해 IDE 스타일의 레이어드 다크 팔레트를 사용할 수 있다.
- IDE 스타일 다크 모드는 `깊은 배경`, `채워진 패널`, `은은한 보더`, `차분한 버튼`, `낮은 채도의 강조`를 사용한다.
- 현재 승인된 다크 프리셋 기준은 `Cursor Dark (기본 테마)`다.
- 라이트 모드도 다크 모드처럼 강한 순백 대비보다 소프트 그레이 레이어를 우선한다.
- 라이트 모드의 화면 구분은 `배경 1단계 차이 + 얇은 보더`만으로 해결한다.
- 라이트 모드에서 새하얀 카드와 검은 텍스트의 과도한 대비는 지양한다.

## Typography
- 기본 폰트: `Inter`, `SF Pro Text`, `Segoe UI`, `system-ui` 순의 산세리프 스택
- 본문 크기: `16px`
- 제목 크기: `20px ~ 28px`
- 권장 두께: `400`, `500`, `600`, `700`
- 숫자와 상태값은 읽기 쉬운 대비를 유지한다.
- 다크 모드에서 폰트는 Cursor Dark처럼 차분한 시스템 산세리프 인상을 유지한다.
- 지나치게 둥글거나 장식적인 폰트는 사용하지 않는다.

## Layout
- 기본 구조는 `Header + Content` 또는 `Sidebar + Header + Content`를 사용한다.
- 주요 업무 화면은 넓은 본문 영역을 우선 확보한다.
- 카드, 폼, 테이블은 동일한 간격 체계를 따른다.
- 한 화면 안에서 주요 액션은 시각적으로 분리한다.
- 구분선은 정보 블록을 나누는 용도로만 최소한으로 사용한다.
- 다크 모드 구분선은 강한 대비보다 낮은 대비의 얇은 라인을 사용한다.
- 라이트 모드 구분선도 진한 회색이 아니라 낮은 대비의 얇은 라인을 사용한다.

## Grid
- Desktop, Tablet, Mobile을 모두 지원한다.
- Desktop 우선으로 설계하되, Tablet과 Mobile에서 핵심 기능 접근이 가능해야 한다.
- 복잡한 운영 화면은 Desktop 기준 다단 구성을 허용한다.

## Header
- 헤더에는 현재 위치, 주요 액션, 사용자 상태를 표시한다.
- 글로벌 액션은 우측 정렬을 기본으로 한다.
- 동일한 앱 전체에서 헤더 구조를 최대한 통일한다.

## Title
- 모든 화면과 컴포넌트는 사용자가 이해하기 쉬운 `title`을 반드시 제공한다.
- `title`은 한국어로 작성한다.
- 예시
  - `title="회원정보"`
  - `title="알림"`
  - `title="로그아웃"`
  - `title="기사목록"`
  - `title="오더등록"`

## Sidebar
- 관리/운영 화면이 확장되면 Sidebar를 사용한다.
- 선택된 메뉴는 배경 또는 텍스트 대비로 구분한다.
- 메뉴 구조는 업무 흐름 순서에 맞춘다.
- 아이콘은 장식보다 탐색 보조 용도로만 사용한다.

## Footer
- 운영 UI에서는 Footer 비중을 낮춘다.
- 필요한 경우 버전, 저작권, 운영 정보만 간단히 표시한다.

## Card
- 카드 스타일은 공통 규칙을 따른다.
- 배경: White
- 라이트 모드 카드 배경은 순백이 아니라 주변보다 한 단계 밝은 중립 회색을 사용한다.
- 테두리: Gray Border
- Radius: `10px`
- Shadow: 기본적으로 사용하지 않음
- Padding: `16px`
- 카드 내부에는 하나의 정보 묶음만 넣는다.
- 다크 모드 카드 규칙
  - 중요하지 않은 카드는 배경색을 넣지 않는다.
  - 중요한 카드도 기본적으로 배경색을 넣지 않는다.
  - 카드 배경 강조는 사용자가 별도로 지시했을 때만 허용한다.
  - 카드 중요도는 화면 목적과 정보 우선순위에 따라 제한적으로 사용한다.
  - 한 화면에서 많은 카드를 동시에 강조하지 않는다.
- 카드 강조 단계
  - 기본 카드: 배경색 없음
  - 보조 강조 카드: 별도 지시 전까지 사용 금지
  - 핵심 강조 카드: 별도 지시 전까지 사용 금지
  - 별도 지시 없이는 배경 강조를 만들지 않는다
- IDE 스타일 다크 모드 예외
  - 기본 패널은 깊은 다크그레이 배경을 사용할 수 있다.
  - 보조 패널은 기본 패널보다 한 단계 밝은 다크 배경을 사용할 수 있다.
  - 레이어 차이는 검정이 아니라 다크그레이 계층으로 만든다.

## CSS Class Naming
- 공통 CSS 클래스 이름은 스타일 자체보다 역할과 의미를 우선해서 작성한다.
- `btn-primary`, `panel-dark`, `input-field`처럼 시각 표현 중심 이름보다 `action-button--primary`, `surface-card--raised`, `form-control`처럼 역할 중심 이름을 우선한다.
- 새 공통 클래스는 가능한 한 아래 패턴을 따른다.
  - Surface: `surface-card`, `surface-card--muted`, `surface-card--raised`
  - Action: `action-button`, `action-button--primary`, `action-button--secondary`
  - Form: `form-control`, `form-select`
  - Badge: `meta-badge`
  - Icon Button: `icon-button`
  - Content Block: `block-title`, `block-description`
- 기존 클래스가 남아 있더라도 새 작업에서는 semantic 클래스 사용을 우선한다.

## Button
- 버튼은 역할별로만 구분한다.
- 버튼은 의미를 명확하게 아이콘으로 표현할 수 있으면 가능한 한 아이콘 우선으로 구성한다.
- 반복적으로 자주 사용하는 공통 액션은 텍스트 버튼보다 아이콘 버튼 또는 아이콘 중심 버튼을 우선한다.
- 의미가 모호하거나 오해 가능성이 있는 버튼만 `아이콘 + 텍스트` 구성을 사용한다.
- 텍스트만 있는 버튼보다 아이콘이 포함된 구성을 우선한다.
- 아이콘 버튼은 반드시 `title` 또는 `aria-label`을 제공한다.
- 기본 버튼
  - Gray Background 또는 Transparent Background
  - Dark Gray Text
  - Gray Border
  - Radius `8px`
  - Height `44px`
- 라이트 모드 버튼은 흰색 채움보다 연한 회색 채움을 우선한다.
- 보조 버튼
  - Light Gray Background 또는 Transparent Background
  - Gray Border
  - Gray Text
- Hover
  - Gray 또는 Dark Gray 단계 안에서만 변화
- Disabled 버튼
  - Transparent 또는 Very Light Gray Background
  - Gray Text
- 버튼 색상 규칙
  - 포인트 컬러 버튼을 만들지 않는다.
  - 버튼은 무채색 보더와 텍스트 중심으로 구성한다.
  - 중요도 차이는 색상보다 텍스트 두께, 배치, 순서로 먼저 구분한다.
  - 다크 모드에서도 버튼 배경은 기본적으로 채우지 않는다.
  - 버튼 강조 배경은 사용자가 별도로 지시했을 때만 허용한다.
- IDE 스타일 다크 모드 예외
  - Primary 버튼은 채워진 다크그레이 배경을 사용할 수 있다.
  - Secondary 버튼은 한 단계 낮은 다크그레이 배경을 사용할 수 있다.
  - Hover는 밝은 색이 아니라 더 선명한 다크그레이 단계로 처리한다.
  - Hover 시 버튼 텍스트는 기본 상태보다 한 단계 더 밝아져야 한다.
- 예시
  - `저장`
  - `추가`
  - `삭제`

## Icon Action
- 아이콘은 장식보다 행동 의미 전달용으로 사용한다.
- `추가`, `수정`, `삭제`, `검색`, `새로고침`, `설정`, `닫기`, `메뉴`, `다운로드`, `업로드`처럼 공통성이 높은 액션은 가능한 한 아이콘으로 우선 표현한다.
- 사용자가 한눈에 이해하기 어려운 액션, 처음 등장하는 액션, 파괴적 액션은 `아이콘 + 텍스트`를 유지한다.
- 좁은 툴바, 테이블 액션, 헤더 유틸리티 액션은 아이콘 버튼을 우선한다.
- 메뉴와 드롭다운 항목은 기본적으로 `아이콘 + 텍스트`를 유지한다.

## Input
- 모든 Input은 동일한 시각 규칙을 사용한다.
- Input에는 가능한 한 `placeholder`와 `title`을 함께 제공한다.
- 예시

```html
<input
    title="회원 이름"
    placeholder="회원 이름을 입력하세요"
/>
```
- 배경: White
- 라이트 모드 Input은 흰색 필드보다 연한 회색 Surface를 우선한다.
- Border: Gray
- Radius: `8px`
- Focus: 진한 검정보다 한 단계 진한 Gray Border
- Shadow는 사용하지 않는다.

## Select
- Input과 동일한 높이와 라운드 값을 유지한다.
- 선택 상태와 비활성 상태를 명확히 구분한다.
- Select 역시 포인트 컬러 없이 Gray Border와 Gray Surface만 사용한다.
- 라이트 모드 Select도 페이지 배경과 완전히 같은 흰색을 사용하지 않는다.
- 다크 모드에서는 Select 배경을 기본적으로 투명하게 유지한다.

## Checkbox / Radio
- 기본 폼 요소와 같은 색상 체계를 사용한다.
- 선택 여부가 명확히 보이도록 대비를 유지한다.

## Table
- White Background
- Gray Border
- Hover Gray
- Striped는 사용하지 않는다.
- 정렬, 상태, 액션 컬럼은 항상 일정한 규칙을 유지한다.
- 대량 데이터 화면에서는 검색, 필터, 페이지네이션을 기본 제공한다.

## Modal
- 중요 확인, 수정, 상세 조회에만 사용한다.
- Radius: `10px`
- 한 모달 안에 과도한 단계의 작업을 넣지 않는다.
- 삭제와 파괴적 작업은 반드시 확인 UI를 거친다.

## Badge
- 상태 표현용으로만 사용한다.
- 색상은 `Normal`, `Info`, `Warning`, `Danger` 체계를 따른다.
- 배지 텍스트는 짧고 명확해야 한다.
- 기본 Badge는 무채색만 사용한다.
- 의미 색상 Badge는 별도 지시가 있을 때만 사용한다.

## Toast
- 저장 완료, 실패, 경고, 안내 메시지에 사용한다.
- 성공/실패 여부가 즉시 구분되어야 한다.
- 같은 메시지를 반복 노출하지 않는다.

## Form
- 폼은 위에서 아래로 읽는 단일 흐름을 기본으로 한다.
- 라벨, 입력창, 오류 메시지 순서를 유지한다.
- 필수 입력과 선택 입력을 구분한다.
- 서버 검증 오류는 입력 필드 근처에 표시한다.
- 공통 입력은 `shared/components/Form/`의 `BaseInput`, `BaseTextarea`, `BaseSelect`, `BaseCheckbox`, `BaseMarkdownEditor`를 우선 사용한다.

## Dashboard
- 첫 화면은 상태 요약, 주요 액션, 예외 상황을 빠르게 보여줘야 한다.
- KPI 카드, 최근 작업, 경고 목록은 우선순위가 높은 순서대로 배치한다.
- 장식용 위젯보다 운영 가치가 있는 정보가 우선이다.

## Dispatch UI
- 배차 화면은 실시간 상태 변화와 충돌 방지가 핵심이다.
- 필수 정보
  - 오더 상태
  - 기사 상태
  - ETA
  - 추천 기사
  - 대기열 여부
- 자동 배차와 수동 배차의 차이를 명확히 보여줘야 한다.
- 위험 상태는 색상과 문구로 동시에 표현한다.

## Mobile UI
- 모바일에서는 핵심 액션만 남기고 부가 정보는 접는다.
- 큰 테이블은 카드형 또는 요약형으로 변환 가능해야 한다.
- 터치 환경 기준으로 버튼과 입력창 간격을 충분히 확보한다.

## Icon
- 아이콘 라이브러리: `Lucide Icons`
- 프로젝트 전체에서 하나의 아이콘 라이브러리만 사용한다.
- 현재 권장 기준은 `Lucide Icons`다.
- Vue 3 프로젝트에서는 `lucide-vue-next` 사용을 권장한다.
- 새로운 아이콘 라이브러리를 임의로 추가하지 않는다.
- 모든 아이콘은 공통 `Icon` 컴포넌트 또는 공통 Wrapper를 통해 사용한다.
- 직접 SVG를 반복 작성하지 않는다.
- 단색만 사용한다.
- 권장 크기: `20px ~ 24px`
- 장식용 아이콘보다 의미 전달용 아이콘만 사용한다.
- 텍스트만 표시하지 않고, 가능한 모든 UI에는 적절한 아이콘을 함께 사용한다.
- 메뉴는 `아이콘 + 텍스트` 구성을 기본으로 한다.
- 예시
  - `회원정보`
  - `로그아웃`
  - `알림`
  - `설정`

## Menu
- Dropdown Menu는 `아이콘 + 텍스트` 형태를 기본으로 한다.
- 예시
  - `회원정보`
  - `설정`
  - `비밀번호 변경`
  - `로그아웃`

## 접근성
- 모든 버튼과 아이콘 버튼은 `title` 또는 `aria-label`을 반드시 제공한다.
- 예시

```html
<button
    title="로그아웃"
    aria-label="로그아웃">
</button>
```

## Radius
- Button: `8px`
- Input: `8px`
- Card: `10px`
- Modal: `10px`

## Shadow
- 기본적으로 사용하지 않는다.
- 필요한 경우 매우 약한 Shadow만 허용한다.
- Shadow는 깊이감 표현보다 구분용으로 제한적으로 사용한다.

## Animation
- 기본적으로 사용하지 않는다.
- 필요한 경우 Fade 정도의 최소 애니메이션만 허용한다.
- 시각 효과가 성능과 업무 속도를 방해하면 제거한다.

## 공통 컴포넌트
- 반드시 공통 컴포넌트를 우선 사용한다.
- 대상 컴포넌트
  - Button
  - Card
  - Input
  - Select
  - Checkbox
  - Radio
  - Table
  - Modal
  - Drawer
  - Dialog
  - Badge
  - Toast
  - Loading
  - Empty
  - Pagination
  - Search
  - DatePicker

## UX 규칙
- 한 화면은 하나의 핵심 목적을 가진다.
- 3번 이하의 클릭으로 주요 기능에 접근할 수 있어야 한다.
- 삭제는 반드시 확인창을 띄운다.
- 저장 완료 후 Toast 또는 명확한 성공 메시지를 표시한다.
- 비동기 처리 중에는 Loading 상태를 보여준다.
- 데이터가 없으면 Empty 상태를 표시한다.
- 실패는 조용히 숨기지 말고, 사용자에게 복구 가능한 형태로 보여준다.

## 디자인 금지사항
- Gradient
- Glassmorphism
- Neumorphism
- Glow
- 3D Effect
- 과도한 Shadow
- 화려한 색상 남용
- 무지개 색상
- 장식용 아이콘 남용
- 과도한 애니메이션
- 중요하지 않은 카드의 불필요한 배경색 사용
- 포인트 컬러 중심의 버튼 스타일
- 기본 요소에 임의의 의미 색상 적용
- Border와 Select에 장식용 색상 적용

## 디자인 변경 규칙
- 새로운 버튼 스타일을 임의로 만들지 않는다.
- 새로운 카드 스타일을 임의로 만들지 않는다.
- 새로운 입력창 스타일을 임의로 만들지 않는다.
- 새로운 색상을 무분별하게 추가하지 않는다.
- 기존 디자인 시스템을 반드시 재사용한다.
- 다크 모드에서 카드 강조가 필요하면 먼저 중요도를 설명한다.
- 중요하지 않은 카드에는 배경색을 추가하지 않는다.
- 버튼은 채운 색상보다 보더 기반 스타일을 우선한다.
- 버튼, 카드, 셀렉트, 보더, 상태 박스는 기본적으로 Gray / Dark Gray 안에서만 수정한다.
- 별도 지시 없는 의미 색상 추가는 금지한다.
- 다크 모드에서도 배경 채움은 기본값이 아니다.
- 다크 모드에서 배경을 넣어야 한다면 반드시 사용자 지시를 먼저 확인한다.
- IDE 스타일 다크 모드를 적용할 때도 원색, 네온, 과한 글로우는 금지한다.
- 화이트 모드 역시 순백 기반의 화려한 SaaS 스타일로 되돌리지 않는다.
- 라이트/다크 어느 쪽이든 과한 대비, 불필요한 강조, 장식용 색상 추가는 금지한다.
- 새로운 화면을 만들 때는 먼저 현재 공통 컴포넌트와 이 문서의 레이어 규칙에 맞춰 설계한다.

## AI UI 규칙
- AI는 기존 디자인 시스템을 반드시 따른다.
- 페이지마다 새로운 디자인 언어를 만들지 않는다.
- 기존 컴포넌트를 우선 사용한다.
- 동일한 기능은 동일한 UI를 사용한다.
- 공통 컴포넌트를 수정할 경우 영향 범위를 먼저 설명한다.
- AI는 다크 모드에서 카드 중요도를 임의로 높이지 않는다.
- AI는 버튼에 포인트 컬러를 추가하지 않는다.
- AI는 카드 배경색보다 정보 구조와 우선순위로 중요도를 표현한다.
- AI는 Select, Border, Error Box, Toast에도 임의 색상을 넣지 않는다.
- AI는 사용자가 색상을 지정하기 전까지 무채색 디자인을 유지한다.
- AI는 다크 모드에서도 컴포넌트 배경을 임의로 채우지 않는다.
- AI는 사용자가 IDE 스타일 다크 모드를 요청한 경우에만 레이어드 다크 팔레트를 사용할 수 있다.
- AI는 화이트 모드도 다크 모드와 같은 수준의 절제된 레이어 구조로 유지해야 한다.
- AI는 UI 작업 전후에 반드시 이 문서 기준과 충돌하는 요소가 없는지 먼저 확인한다.
- AI는 사용자의 새 요청이 있어도 본 문서와 충돌하면 먼저 규칙 기준으로 해석하고 최소 변경만 적용한다.
- AI는 UI 생성 시 가능한 한 `title`, `Icon`, `aria-label`을 기본으로 추가한다.
- 특별한 이유가 없는 한 `title`, `Icon`, `aria-label`을 생략하지 않는다.

## 최종 목표
- 예쁜 UI를 만드는 것이 목표가 아니다.
- 빠르고 단순하며 일관성 있는 업무용 UI를 만드는 것이 목표다.
- 사용자가 UI를 배우는 것이 아니라, 직관적으로 바로 사용할 수 있어야 한다.
