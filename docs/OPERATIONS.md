# 운영 기획 (Operations)

> 상태: ✅ 현행 — 운영 구조·관리자 시스템·자동화의 **단일 소스 문서**다. 제품 방향성은 [PRODUCT_VISION.md](./PRODUCT_VISION.md) 참조.

## 운영 구조

> **관리자 1개 중심 + 기사 앱 / 운행 등록자 / 관리자 시스템 3영역.** 모든 운행은 하나의 상태 시스템으로 관리한다.

**운영 핵심 원칙**: 정상적인 운행은 시스템이 자동으로 처리하고, **문제가 발생한 운행만 관리자가 개입**한다.

## 운행 운영 흐름

```
운행 등록 → 검수 → 마켓 공개 → 기사 추천 → 기사 신청 → 등록자 승인
→ 운행 확정 → 기사 출발 → 픽업 → 운행중 → 운행 완료 → 정산
```

## 관리자 시스템 (관리자 웹 별도 구축)

### 대시보드 (오늘)
신규 운행 / 신청 / 확정 / 운행중 / 완료 / 정산 대기 / 신규 기사 / 신규 등록자 / 신고 — 플랫폼 상태를 한 화면에.

### 운행 관리
- 목록: [전체][신규][매칭][운행중][완료][취소] — 운행번호·출발·도착·시간·금액·기사·등록자·상태
- 액션: 운행 수정 / 숨김 / 취소 / 기사 변경 / 운행 상태 변경 / 등록자 확인

### 기사 관리
- 목록: 기사명·차량·지역·평점·완료 운행·취소율·승인율·상태
- 상세: 최근 운행 / 정산 / 신고 이력 / 채팅 이력
- 기사 상태: 정상 / 주의 / 운행 제한 / 정지

### 등록자 관리
- 목록: 업체명·담당자·등록/완료/취소 운행·평점·정산·상태
- 반복 취소·문제 등록자 관리

### 승인/거절 관리
- 흐름: 기사 신청 → 등록자 승인 요청 → 승인/거절 → 기사 결과 전달
- **운행 타임라인(신청→승인→시작→완료→정산) 전부 기록해 분쟁에 대응한다.**

### 채팅 운영
- 업무센터 역할. 관리자 개입 도구: [대화 확인][운행 보류][정산 보류][관리자 중재]

### 신고/분쟁
- 대상: 기사 / 등록자 / 운행 / 채팅 / 거래
- 유형: 요금 / 취소 / 노쇼 / 주소 오류 / 시간 오류 / 채팅 문제 / 서비스 문제 / 기타
- 처리 흐름: 접수 → 확인 → 조사 → 처리 → 완료

### 일일 운영 화면
- 🔴 **즉시 처리**: 신고 / 분쟁 / 정산 오류
- 🟡 **확인 필요**: 승인 대기 / 취소 요청 / 요금 협의
- 🟢 정상
- **문제 업무를 먼저 처리한다.**

## 자동화

### 흐름
- 운행 자동화: 등록 → 조건 검사 → 기사 추천 → 추천 알림 → 기사 신청 → 등록자 알림 → 승인 → 기사 알림
- 운행 후: 완료 → 정산 자동 생성 → 정산 예정 → 정산 완료 → 기사 알림

### 단계
1. 초기: 자동 추천 + 관리자 검수
2. 성장: 자동 매칭 / 알림 / 정산
3. 확장: 예외만 관리자 처리

> **운영 데이터가 쌓인 뒤 자동화를 확대한다.**

## 자동 매칭 점수 (운행별 적합 기사 상위 N명 추천)

| 항목 | 초기 비율 |
|---|---|
| 차량 | 25% |
| 거리 | 25% |
| 시간 | 20% |
| 동선 | 15% |
| 선호 | 10% |
| 평점 | 5% |

> 운영 데이터가 쌓이면 비율을 조정한다. (홈 추천의 조건 일치율은 [RECOMMENDATION.md](./RECOMMENDATION.md) 참조)

### 구현
- 엔진: `app/Services/DriverMatchRanker.php` (배점·상위 N 설정은 `config/matching.php`)
- 조회: `GET /api/admin/orders/{order}/matching-drivers` (관리자 전용) — 점수(`match_score`)·근거(`reasons`)·항목별(`breakdown`) 반환
- **운행 공개 시 자동 추천 알림**: `MatchService::matchForOrder`가 랭킹 상위 N명 중 **매칭 설정 조건을 실제로 충족한 기사**에게만 '매칭 운행 도착' 알림을 보낸다 (기존 전체 브로드캐스트 → 상위 적합 기사 우선 제안)
- 후보: **온라인 + 매칭 켬 + 활성 매칭 설정 보유** 기사. 같은 날짜 진행 중 일정과 서비스 시간이 실제로 겹치는 기사는 제외(겹치지 않고 이어서 픽업 가능하면 동선 점수로 포함)
- 데이터 제약 사항(프록시):
  - **거리**: GPS 좌표가 없어 '현재 활동 권역'(최근 운행 하차지·자주 가는 지역 상위 토큰)과 픽업지가 같은 구·동이면 만점 처리. 좌표 도입 시 실거리 기반으로 교체
  - **동선**: 같은 날짜 진행 중 일정의 하차지→픽업지, 또는 픽업지→하차지 권역 연결 여부
  - **평점**: 기사가 받은 리뷰 평균(1~5). 리뷰가 없으면 중립 3.0 (신규 기사 불이익 방지)
- 위치 권역 판정 공용 유틸: `app/Support/Orders/LocationTokens.php`

## 알림 운영

- 유형: 신청 / 승인 / 거절 / 채팅 / 시간 변경 / 요금 변경 / 취소 / 운행 시작 / 운행 완료 / 정산 / 시스템 / 공지
- **알림 피로도 관리: 같은 운행에서 불필요한 알림 반복 금지, 관련 이벤트는 하나로 묶는다.**

## 정산 운영

- 흐름: 완료 → 정산 금액 확정 → 수수료 계산 → 정산 대기 → 지급 → 지급 완료
- 데이터: 운행금액 · 플랫폼 수수료 · 추가금 · 환불 · 실제 지급액 · 지급일
- **정산 데이터 변경 이력도 기록한다.**

## 운영 데이터 (개인화 추천의 핵심)

- 운행 데이터: order / ride / driver / customer / vehicle
- 이벤트 데이터: 신청 / 승인 / 거절 / 취소 / 시작 / 픽업 / 완료 / 정산
- 행동 데이터: 추천 노출 / 추천 클릭 / 신청 / 거절 / 취소 / 완료

## 운영 핵심 5가지

1. **운행 관리** — 등록~취소
2. **기사/등록자 관리** — 신뢰도·상태·이력
3. **운행 상태 관리** — 신청→승인→운행→완료 ([ORDER_FLOW.md](./ORDER_FLOW.md))
4. **정산/분쟁 관리** — 금액·수수료·지급·신고·중재
5. **추천/매칭 관리** — 기사 조건·위치·동선·선호

## 초기 운영 전략

- 좁은 시장(인천공항 → 서울)에서 시작: 기사 확보 → 운행 확보 → 매칭 → 운행 → 정산 안정화 후 확대
- 초기 인력: 대표/운영 1명 + 개발 1~2명 + CS/운영 1명
- 확장 시: CS / 운행 관제 / 정산 / 분쟁 / 영업 분리
- 성장 경로: 관리자 중심+자동 추천 → 자동 매칭+자동 알림+자동 정산 → 예외 상황만 관리자 처리 → 기사의 하루 운행 자동 추천
