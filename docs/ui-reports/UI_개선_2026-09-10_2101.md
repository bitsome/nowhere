## (e) 적용하지 않은 항목과 이유 (후보)
1. **`@media` 브레이크포인트 공용 토큰화(5번)**: 앱 화면이 사실상 `480px` 단일 분기로 이미 일관되고, 관리자 `640px` 는 성격이 다른 의도된 값이다. 토큰화 이득이 작고 전역 CSS 변수 추가는 설계 결정 사안 → 후보.
2. **`border-radius: 14px` 하드코딩 15건의 `var(--card-radius)` 치환(6번)**: 값이 **동일(14px)** 해 렌더 결과가 완전히 같다. UI 개선이 아닌 규약 정리이며 14개 파일 일괄 수정이라 회귀 위험 대비 이득이 낮아 후보 유지.
3. **`n-input` 의 `type="number"`/`type="email"` 등 타입 prop 재검토**: `type` 은 naive-ui의 선언된 prop(`String`)이라 런타임 검증을 통과하고 실제 `<input type>` 으로 렌더된다 → 결함 아님. `min`·`max`·`step` 을 쓰는 곳은 전부 `n-input-number` 의 정식 prop이다.
4. **`maxlength` 의 `input-props` 이관**: `maxlength` 는 선언된 prop이고 `inputProps` 스프레드 **이후**에 `maxlength: countGraphemes ? undefined : this.maxlength` 로 덮이므로 오히려 prop으로 두는 것이 정답 → 의도적 미적용.
5. **`transition: all` 1곳([QuickMatchPanel.vue](file:///d:/wwwroot/nowhere/frontend/src/components/orders/QuickMatchPanel.vue#L1089))**: 실제 변하는 속성이 `border-color·color·background` 뿐이지만 어느 쪽이든 시각 차이가 없어 우선순위 제외 → 후보 유지.
6. **하단 네비·ChatList `n-badge` 색/크기 통일**: `naiveThemeOverrides.Badge` 추가 시 프로젝트 `--badge-red`(#e24c4c)가 흰 글자 기준 대비 라이트 3.91:1·다크 4.10:1 로 현재 naive 기본값(4.58:1)보다 **낮아져** 10px 배지 가독성이 떨어진다. 색 통일 + 배지 글자색 규약을 함께 정하는 디자인 결정이 선행돼야 함 → 후보 유지.
7. **`semantic.badgeRed` 사문화**: 배지 색 규약 결정 전에는 삭제·사용 어느 쪽도 이름 → 후보 유지.
8. **커뮤니티 피드 카드 키보드 접근**: `role="button"` 부여 시 내부 좋아요·댓글 버튼과 중첩 인터랙티브가 되고 Enter 버블링으로 카드가 함께 열리는 부작용이 재현된다 → 구조 변경 사안으로 후보.
9. **알림 화면 카운트 배지 radius 혼재(9px/7px/999px)·카피 문체 혼재**: 각각 v8 시안 radius·전역 카피 문체를 정하는 결정 사안 → 후보.
10. **FAB 3곳 흰 글리프 / 관리자 화면 상태 칩 규격 / base.css 레거시 `.btn`·`.card` 죽은 CSS / `:focus-visible`·`outline: none`**: 09-03~09-10 여러 회차에서 반복 분류된 항목으로, 각각 전역 설계 결정 또는 정리 작업 성격 → 기존 분류 유지(반복 미적용).

## (f) 빌드 결과
- **`npm run build` 통과** (vite v8.2.1, `✓ built in 1.02s`, 오류·경고 0건) — 수정 반영 후 실행. `LoginView`·`RegisterView`·`ForgotPasswordView`·`SettlementView`·`OrderCreateView`·`SettingsProfileView` 청크 정상 재생성.
- import 누락 점검: 변경이 **템플릿 속성 이관·추가뿐**이라 import·심볼·컴포넌트 등록 영향 **0건**. `:input-props` 는 인라인 객체 리터럴(`{ inputmode: 'numeric' }` 등)로 외부 식별자를 참조하지 않으므로 누락될 import가 없다. `inputmode="numeric"`(SettlementView)은 네이티브 `<input>` 속성이라 역시 무관.
- 빌드 산출물 검증: `dist/assets` 에서 **`inputmode` 가 4개 청크**(`ForgotPasswordView`·`OrderCreateView`·`SettingsProfileView`·`SettlementView`)에 반영 확인 → `input-props` 경유 속성이 번들까지 실제로 전달됨. `autocomplete` 값(`current-password`·`new-password`)도 `LoginView`·`RegisterView`·`ForgotPasswordView` 청크에 각각 반영 확인.
- 런타임 위험 점검: 속성값을 바꾸지 않았고 전달 경로만 교정했으므로 **회귀 시나리오 없음**. `<n-input>` 의 기존 레이아웃·검증·이벤트(`@keyup.enter`)·`maxlength` 동작은 그대로이며, 새로 적용되는 것은 브라우저의 자동완성·키보드 선택 동작뿐이다. 자동완성 힌트가 없던 화면은 영향 0(속성이 래퍼 div → 실제 input 으로 이동).
