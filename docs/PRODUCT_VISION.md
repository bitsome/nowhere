# 운행 최적화 플랫폼 방향성 (Product Vision)

> 상태: ✅ 현행 — 제품 방향성의 **단일 소스 문서**다. 모든 기능·UI·추천 로직은 본 문서를 따른다.

## 핵심 방향성

> 단순 운행 게시판이 아니라, **"기사님이 오늘 어떤 운행을 받을지 앱이 먼저 골라주는 운행 최적화 플랫폼"**.

- 핵심 가치: **운행을 많이 보여주는 것보다 기사에게 필요한 선택지를 줄이고 판단 피로도를 낮추는 것.**
- 최종 목표 흐름: 앱 실행 → 오늘 받을 운행 추천 → 추천 이유 확인 → 신청 → 채팅 → 승인 → 운행 → 완료 → 정산 → 다음 운행 추천.

## UX 원칙 (UI 미니멀)

1. 한 화면에 Primary 버튼 하나.
2. 현재 해야 할 행동을 가장 크게 표시.
3. 정보 → 추천 이유 → 행동 순서.
4. 색상은 의미가 있을 때만 사용.
5. 홈에는 오늘 필요한 정보만 표시.
6. 부가 기능은 더보기로 이동.
7. 카드·장식 요소 과도한 중첩 금지.
8. 기능을 삭제하지 않고 노출량을 줄인다.

## 추천/매칭 (3단계)

| 단계 | 기준 |
|---|---|
| 1단계 조건 기반 | 차량·지역·시간·거리·금액·공항·운행 가능 여부 |
| 2단계 기사 행동 데이터 | 신청/거절/완료 이력, 선호 지역·시간·금액·차량, 취소 패턴 |
| 3단계 개인화 | 기사별 선호+과거 운행으로 추천 순서 차등화 |

**추천 이유 형식(카드)**: "조건 96%" 스코어 + ✓ 체크리스트(차량 조건 일치 / 현재 위치에서 가까움 / 다음 운행과 동선 좋음 / 시간 여유 충분)

> 구현 기준: `match_score`(조건%)·`match_reasons`(근거 체크리스트)는 [RECOMMENDATION.md](./RECOMMENDATION.md) 참조.

## 홈 구성 (우선순위)

1. 오늘 받을 운행 → 2. 가장 추천되는 운행 → 3. 다음 추천 운행 → 4. 내 일정 → 5. 최소한의 빠른 메뉴

추천 카드: 노선(인천공항 T1 → 강남) / 오늘 13:30 / 3명·캐리어 2 / 금액 / 조건% + 근거 체크 / [운행 확인하고 신청하기]

**홈 추천은 연결고리 / 단일 / 셋트 3개 섹션으로 구성한다.**

## 동선 최적화 (추천의 핵심 차별화)

- 흐름: 현재 위치 → 픽업 → 도착 → 다음 운행
- 근거: 현재 위치와 가까움 · 차량 조건 일치 · 다음 운행과 동선 좋음 · 시간 여유 충분
- 장기 목표: 하루 전체 운행 순서 최적화

## 오늘 수익 최적화 (향후)

- 오늘 목표(예 30만) / 현재 수익 / 부족 금액 표시.
- 목표 달성을 위한 운행 조합 자동 추천으로 발전.

## 화면별 가이드

### 마켓
- 탭: [추천][전체][임박][내 조건]. 홈에서 못 찾았을 때 탐색 공간.

### 운행 상세
- 상태 중심(신청 → 승인 대기 → 승인 → 운행 시작 → 운행중 → 완료 → 정산 대기 → 정산 완료).
- 현재 상태 + 다음 행동 하나를 가장 크게.

### 채팅
- 운행 업무센터: 승인/거절/시간 변경/요금 협의/취소 요청 버튼, 운행 중엔 픽업도착/탑승/시작/완료.
- 주요 행동은 운행 기록에 남긴다.

### 알림센터 색상
- 민트 = 완료/정상/주요 행동
- 옐로우 = 요금·시간 변경/확인 필요
- 레드 = 취소/거절/문제
- 블루 = 채팅/정보
- 퍼플 = 항공편
- 그레이 = 시스템
- 우선순위: 처리 필요 > 확인 필요 > 완료 > 일반 정보

### 내 운행
- 구성: [전체][오늘][예정][운행중][완료] 지향.
- 검색: 날짜·지역·상태·금액·출발지·도착지.

### 정산
- 기사 관점: 출금 가능 / 이번 달 / 출금하기.
- 금액 = 옐로우, 완료 = 민트, 문제/보류 = 레드.

### 더보기 구성
- 기사 프로필 / 운행 관리(내 운행·매칭 설정·정산) / 운행 도구(항공편 조회·여행지 주차·알림센터) / 커뮤니티(커뮤니티·쇼핑중고거래) / 내 차량·계정 / 고객지원(공지·FAQ·문의)

### 하단 메뉴 5개 유지
- 홈(오늘 받을 운행) | 마켓(운행 탐색) | 커뮤니티(기사 정보/거래) | 채팅(운행 업무) | 더보기(설정/부가 기능)

## 사업·우선순위

### 단계
- **MVP 1차**: 홈 / 오늘 받을 운행 추천 / 마켓 / 운행 상세 / 신청·승인·거절 / 채팅 / 운행 시작·완료 / 내 운행 / 정산 / 알림
- **2차**: 차량 관리 / 매칭 설정 / 기사 프로필·평점 / 커뮤니티
- **3차**: 쇼핑·중고거래 / 항공편 / 주차 / 여행지
- **장기**: 개인화 추천 / 동선 최적화 / 오늘 수익 최적화 / 자동 운행 계획

### 시장 전략
- 인천공항↔서울 → 김포+수도권 → 수도권 전체 → 전국.
- 초기에 운행+기사 균형 확보.

### 수익모델
- 운행료 5% 수수료
- 등록자 구독: Basic 2.9만 · Pro 5.9만 · Business 9.9만
- 장기적으로 기사 무료 + 등록자 유료
- 상세 구조·우선순위·실행 순서는 아래 [수익 구조 (Monetization)](#수익-구조-monetization) 참조.

### 차별화 메시지
> **"오늘 어떤 운행을 받을지 고민하지 않도록 해주는 앱"** — 기능 수로 경쟁하지 않는다.

# 수익 구조 (Monetization)

> 상태: 🔵 설계 — 수익화의 단일 기준. 실행 항목이 구현되면 근거 파일과 함께 갱신한다.

## 기본 원칙
1. **기사에게서 받지 않는다.** 기사 앱은 무료가 정체성이다 — 수익은 등록자(운행을 부탁하는 쪽)와 거래에서 만든다.
2. **추천은 돈으로 바뀌지 않는다.** "앱이 먼저 골라주는 것"이 핵심 자산이므로, 결제가 추천·노출 순위를 바꾸는 구조는 도입하지 않는다. 유료화는 추천 품질 밖(수수료율·운영 대행·도구)에서만 한다.
3. **거래가 있어야 수익이 있다.** 구독은 거래량이 쌓인 등록자에게만 의미가 있다 — 초기에는 수수료 하나로 간다.
4. 수익 축은 **① 거래 수수료 → ② 등록자 구독 → ③ 부가·제휴** 순서로 연다.

## 수익 축

### 1축 — 운행 거래 수수료 (기본 엔진, 지금 수익이 나는 유일한 축)
- 구조: 완료·정산된 운행의 **운행금액 × 수수료율**을 플랫폼이 가져가고, 나머지를 기사에게 지급한다.
- 흐름: 운행 완료 → 정산 생성(gross·fee·net 확정) → 기사 출금 요청 → 관리자 지급.
- 매출 공식: `월 수수료 매출 = 완료 운행 건수 × 평균 운행금액 × 실효 수수료율`
- 현재 구현: 요율 5% 고정(`app/Services/Settlement/SettlementService.php`의 `FEE_RATE` 상수), `settlements`(gross_amount / fee_amount / net_amount), 자동 정산(`config/settlement.php`의 `auto_after_hours`), 기사 출금(`payout_requests`)까지 동작한다.
- 즉시 보완(돈을 더 벌기보다 **요율을 다룰 수 있게** 만드는 일):
  - `FEE_RATE` 상수 → `config('settlement.fee_rate')`로 승격.
  - 등록자별 요율 적용 — `settlements.registrant_id`가 이미 있으므로 등록자 등급별 요율 조회로 확장 가능.
  - 관리자 화면에서 요율·정산 보류를 다루도록 노출(현재는 조회·보류만 있고 요율 조작 UI 없음).

### 2축 — 등록자(업체) 구독 (반복 매출의 본체)
기사는 무료, **운행을 등록하는 업체가 구독료를 낸다.** 구독의 실질 혜택은 "수수료 인하 + 운영 대행"이다. 수수료율만 내려도 구독료보다 이득이 되는 지점이 생겨야 팔린다.

| 플랜 | 월 구독료(가정) | 수수료율(가정) | 핵심 혜택 |
|---|---|---|---|
| 무료 | 0원 | 5% | 월 등록 한도, 기본 정산 |
| Basic | 2.9만 | 4% | 등록 한도 확대, 월간 정산 리포트 |
| Pro | 5.9만 | 3% | 일괄·자동 등록, 담당자 다수, 정산 주기 단축 |
| Business | 9.9만 | 2% | 전담 운영 대행(정산·분쟁), 우선 CS, 브랜드 노출 |

- 구독 성립 조건(손익분기): `월 운행금액 × (기본요율 − 플랜요율) > 월 구독료`. 예: 월 1,200만원을 등록하는 업체가 Pro(5%→3%)로 가면 월 24만원 절감 vs 구독료 5.9만원 → 구독 유인이 성립한다.
- 필요한 구현: 플랜·구독 테이블/모델(현재 미구현), 등록자별 적용 요율, 구독 결제(PG, 현재 미구현), 관리자 플랜 관리.
- 시점: **초기에는 열지 않는다.** 등록자 볼륨이 확보되기 전 구독을 강제하면 공급(운행)이 먼저 빠진다.

### 3축 — 기사 부가 상품 (추천 품질을 건드리지 않는 범위만)
- 허용: 즉시 출금(수수료 소액), 정산·운행 통계 리포트, 제휴 할인(정비·보험·세차·주차), 커뮤니티 부가 기능.
- 금지: 추천 순위 상향, 우선 노출, 조건% 조작 — 추천 신뢰가 무너지면 앱의 존재 이유가 사라진다.
- 시점: 2축 이후. 기사 과금은 "선택 기능"에만 한정한다.

### 4축 — 제휴·커머스 (후순위)
- 항공편·주차·정비·보험 제휴 수수료, 커뮤니티 중고거래/쇼핑 거래 수수료.
- 현재 상태: 커뮤니티 카테고리 라벨(`frontend/src/utils/communityCategories.js`의 `쇼핑·중고거래`)만 있고 상품·주문·결제 코드는 없다 — 신규 개발 영역.

### 5축 — 데이터·리포트 (장기)
- 개인정보 없는 **집계 데이터**만 상품화: 공항 수요·노선·시간대·요금 시세 리포트(등록자·기관 대상).
- 조건: 거래 데이터가 충분히 쌓인 뒤. 개인·업체 식별 정보는 포함하지 않는다.

## 정산·수익 배분 규칙
- `운행금액(gross)` = 등록자가 지불한 총액 → `플랫폼 수수료(fee)` = gross × 요율 → `기사 지급액(net)` = gross − fee.
- 구독료는 운행금액과 분리해 별도 청구한다(운행 정산에 섞지 않는다).
- 분쟁·보류: 관리자 정산 보류(`admin_hold`) 상태는 출금 대상에서 제외하고, 해제 후 지급한다.
- 상태: 정산 `pending → paid`, 출금 요청 `pending → paid / rejected`(거절 시 사유 기록, 정산은 pending으로 복귀).

## 단위 경제 (예시 — 실제 데이터가 아닌 가정)
- 가정: 인천공항 → 서울 1건 평균 12만원, 수수료율 5% → **건당 6,000원**.
- 기사 10명 × 5건/일 = 50건/일 → 일 30만원 → **월 약 900만원**.
- 기사 100명 × 5건/일 = 500건/일 → 일 300만원 → **월 약 9,000만원**.
- 위 숫자는 규모 감각용 가정이며, 실제 요율·단가는 운영 데이터로 확정한다.

## 우선순위와 실행 순서
1. **지금** — 수수료 5% 정산·출금이 실제로 돌게 유지하고, 요율을 config·관리자로 다룰 수 있게 만든다(매출 실현 기반).
2. **다음** — 거래량·등록자 볼륨 확보(인천공항↔서울). 이 단계의 목표는 매출이 아니라 **양면 균형**이다.
3. **그 다음** — 등록자 구독 판매(요율 차등 + 운영 대행). 이때 PG 결제 연동이 필요하다.
4. **이후** — 기사 부가·제휴·커머스, 장기적으로 데이터 리포트.

## KPI (수익 판단 지표)
- 거래액(GMV) / 플랫폼 수수료 매출 / 실효 수수료율
- 활성 기사 수 / 활성 등록자 수 / 완료 운행 건수
- 구독 MRR / 구독 전환율(등록자 대비) / 이탈률
- 취소율 / 정산 리드타임 / 미지급 정산 잔액

## 리스크와 금지선
- **추천·노출 유료화 금지** — 단기 매출보다 추천 신뢰가 우선이다.
- **기사 과금 최소화** — 기사 이탈은 곧 운행 이탈이다.
- **등록자 조기 구독 강제 금지** — 공급이 먼저 빠진다. 거래량 후 구독.
- **요율 상수 고정** — 요율을 바꿀 수 없으면 시장별 실험도, 구독 설계도 불가능하다(최우선 해소 대상).
- **구독료와 운행 정산 혼합 금지** — 정산 금액이 흐려지면 분쟁 근거가 무너진다.
