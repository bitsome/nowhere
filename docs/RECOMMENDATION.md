# 운행 추천 알고리즘

홈 '강력추천'·'추천일정'에 노출되는 운행 추천의 기준을 정의한다.
구현: `app/Services/Order/OrderListService::recommendations()`

## 0. 서비스 지역 (서울 / 인천 / 경기만)

현재 서비스는 **서울, 인천, 경기도 지역의 운행만 취급**한다.

- 추천 대상(왕복 노선·매칭 설정·운행 이력)은 **시작지와 도착지 모두 서비스 지역 안**인 운행만 포함한다.
- 서비스 지역 밖 시·도(부산, 대구, 광주, 대전, 울산, 세종, 강원, 충청, 전라, 경상, 제주)가 명시된 운행은 추천에서 제외한다.
- 시·도명이 없는 상세 지명(판교, 잠실, 여의도 등)은 서울/경기 지역으로 간주한다.
- **공항 구분**
  - 인천공항: `T1`, `T2`
  - 김포공항: `국내선`, `국제선`
  - 같은 공항의 터미널·선은 서로 연결된다. (예: `김포공항 국내선` ↔ `김포공항 국제선`, `인천공항 T1` ↔ `T2`)

## 1. 핵심 패턴 — 샌딩(Send) ↔ 랜딩(Landing) 시간대

운행은 **샌딩(승객 실어 나르기) → 랜딩(내려주기)** 를 반복하는 흐름이다.
가장 기본이 되는 추천 알고리즘은 이 두 구간 사이의 시간 간격으로 정의한다.

| 구간 | 간격 기준 | 범위 |
|---|---|---|
| **샌딩 → 랜딩** | 샌딩 시작 시각 기준 | **30분 ~ 2시간** 사이 |
| **랜딩 → 샌딩** | 랜딩 시작(service_time) 시각 기준 | **3시간 ~ 6시간** (랜딩 + 3시간 이후) |

> **랜딩 → 샌딩은 랜딩 + 3시간 이후부터 연결한다.**
> - 랜딩(공항→도심) 운행을 마친 뒤 다음 샌딩(도심→공항)은 **랜딩 시작 시각 + 3시간 이후**에만 이어진다.
>   (예) 랜딩 14:30 → 다음 샌딩은 **17:30 이후**부터 연결)
> - 설정: `config/recommendation.php`의 `landing_send_gap_hours` (env `LANDING_SEND_GAP_MIN_HOURS`/`LANDING_SEND_GAP_MAX_HOURS`, 기본 **3시간~6시간**)

> **샌딩 → 랜딩 30분~2시간**: 랜딩(공항 픽업) 운행의 시작 시각이 직전 샌딩 시작 후 30분~2시간 이내면 연결한다.
> - 설정: `config/recommendation.php`의 `send_landing_gap_minutes` (env `SEND_LANDING_GAP_MIN_MINUTES`/`SEND_LANDING_GAP_MAX_MINUTES`, 기본 30분~120분)

### 예시 (왕복 체인 기준)

```
14:00 샌딩 ──(30분)──▶ 14:30 랜딩
                         │
                    (랜딩 + 3시간 대기)
                         │
                         ▼
         17:30 샌딩 ──(30분)──▶ 18:00 랜딩
```

- 샌딩 14:00 → 랜딩 14:30  (샌딩→랜딩 30분, 범위 내)
- 랜딩 14:30 → 다음 샌딩 17:30  (랜딩 + 3시간, 범위 내)
- 다음 샌딩 17:30 → 랜딩 18:00  (샌딩→랜딩 30분, 범위 내)

즉, 추천 대상 운행은 **내 이전 운행(랜딩) + 3시간 이후에 시작되는 샌딩** 또는
**샌딩 후 30분~2시간 내에 시작하는 랜딩** 구조를 이어붙일 수 있는 운행을 우선한다.

## 1-1. 지역 연속성 규칙

연속 운행은 **하차지와 다음 출발지가 가까운 위치**일 때만 연결된다. 같은 시/도(서울/인천/경기)만으로는 연결하지 않는다.

- **연결 허용(모두 강력추천)** — **양방향 왕복(공항 샌딩↔랜딩)** 이면서 하차지와 출발지가 **같은 구/동/읍/면(상세 구역)** 이거나 **같은 공항(터미널·선 무관)** 이면 강력추천으로 연결된다.
  - 예) 하차 `인천공항 T1`(샌딩 하차) → 출발 `인천공항 T2`(랜딩 출발) (같은 공항·터미널 다름, 강력추천)
  - 예) 하차 `김포공항 국내선`(샌딩 하차) → 출발 `김포공항 국제선`(랜딩 출발) (같은 공항·선 다름, 강력추천)
  - 예) 하차 `서울 마포구`(랜딩 하차) → 출발 `서울 마포구`(샌딩 출발) (같은 구, 강력추천)
- **양방향 필수** — 강력추천은 반드시 **공항 왕복(샌딩↔랜딩)** 만 연결한다. 샌딩(도심→공항) 다음에는 랜딩(공항→도심)만, 랜딩 다음에는 샌딩만 이어진다. **공항을 오가지 않는 도심↔도심 픽업은 방향이 이어지지 않으므로 강력추천에서 제외한다.**
  - 예) 하차 `서울 강남구`(랜딩) → 출발 `서울 강남구`(도심→도심 픽업, 샌딩 아님 → 양방향 아님 → 제외)
  - 예) 하차 `서울 강남구`(랜딩) → 출발 `서울 성남시`(도심→도심 → 양방향 아님 → 제외)
- **연결 안 됨** — 같은 시/도 안이어도 구/상세 구역이 다르면 연결하지 않는다. (경기 도내 먼 시/군 연결 방지)
  - 예) 하차 `서울 중구` → 출발 `서울 강남구` (같은 서울이지만 구가 다름 → 연결 안 됨)
  - 예) 하차 `경기 고양시` → 출발 `경기 수원시` (같은 경기지만 시/군이 다름 → 연결 안 됨)
  - 예) 하차 `김포공항 국내선` → 출발 `경기 수원시` (가까운 위치 아님 → 연결 안 됨)
  - 예) 하차 `서울 마포구` → 출발 `부산 해운대구` (매칭 안 됨)

### 연속 체인 예시

```
서울 잠실 ──샌딩──▶ 인천공항 T2   (오늘 22:00)
인천공항 T1 ──랜딩──▶ 서울 강남구  (내일 01:00, 야간 → 다음 출발 02:00~03:00 창)
서울 강남구 ──샌딩──▶ 인천공항 T2  (같은 구(강남) + 랜딩→샌딩 왕복 → 강력추천)
인천공항 T1 ──랜딩──▶ 서울 강남구  (같은 공항 + 샌딩→랜딩 왕복 → 강력추천)
```

- **연결 운행은 양방향 연속 체인**으로 추천한다. 연결1을 탄 뒤 차량이 도착하는 하차지(예: 인천공항)에서 시작하는 **연결2→연결3→연결4**까지 이어지는 체인을 함께 추천한다.
- **출발지 = 차량 위치**: 추천 운행의 출발지는 반드시 직전 운행의 하차지(차량이 있는 곳)와 연결되어야 한다. 공운행이 생기지 않도록 방향이 자연스럽게 번갈아 가며 이어진다.
- **강력추천은 반드시 양방향(공항 왕복)** 이다. 샌딩(도심→공항) 뒤에는 랜딩(공항→도심)만, 랜딩 뒤에는 샌딩만 연결되고, 도심↔도심 픽업처럼 공항을 오가지 않는 방향은 체인에서 제외된다.

## 2. 추천 우선순위

- 홈은 **강력추천(양방향 왕복)만** 노출한다. (추천일정·매칭 설정·이력 단건 추천은 홈에서 표시하지 않는다)
  - 맡은 운행이 있으면 그 하차지에서 이어지는 왕복 체인을, **맡은 운행이 없으면 마켓에서 샌딩(도심→공항)을 시작점으로 랜딩(공항→도심)→샌딩→… 이어지는 왕복 체인**을 만들어 보여준다. 왕복이 없으면 빈 상태로 둔다.

1. **연결 운행(강력)** — 현재 맡은 운행(수락/운행중)의 하차지와 같은 구·같은 공항에서 시작하고, **공항 왕복(샌딩↔랜딩) 방향**이 이어지는 운행
2. **마켓 왕복 체인** — 맡은 운행이 없으면 마켓에서 샌딩(도심→공항)을 앵커로, 같은 공항 랜딩(공항→도심) → 같은 구 샌딩 → …으로 최대 5다리까지 왕복 체인으로 추천 (가장 빠른 샌딩 우선, 최대 3개 체인)
   - **순위**: 활성 매칭 설정 **시간대에 맞는 체인을 먼저 정렬**해 내려준다(`recommend_order=1` → `2`). 홈에서는 체인별로 그룹을 나누고, **표시 순서대로 추천1 → 추천2 → 추천3** 번호를 붙인다. (추천 수 = 표시된 체인 수)
   - **일괄요청**: **추천1 체인**에 한해 체인 라인 우측에 '일괄요청' 버튼을 두어, 체인에 포함된 운행들을 각 등록자에게 **한 번에 가져오기 요청**한다. (`POST /api/orders/batch-claim`) 한 건이 실패해도 나머지는 계속 진행하고, 성공/실패 건수를 요약해 알려준다.

## 3. 시간 창 (오늘~내일 중심)

- 기본적으로 **지금부터 4시간 이내에 시작하는 운행**만 추천한다.
  - 예: 오늘 23:00이면 내일 03:00까지 (자정을 넘기는 4시간 창)
- **왕복 노선은 예외** — 복귀 운행 시각이 '랜딩 + 간격 창(샌딩→랜딩 30분~2시간 / 랜딩→샌딩 3시간~6시간)'으로 정해지므로 지금 기준 4시간 창을 적용하지 않고, 직전 운행 기준 창만 따른다. (과거 시작 운행 제외는 동일)
- **매칭 설정 조건에 맞는 운행은 4시간 창 밖이어도 추천**한다. (알람(매칭 알림)과 동일 기준)
- **과거에 이미 시작한 운행은 추천하지 않는다** (지금부터만).
- 이력 기반 추천(자주 다니는 노선·자주 운행한 시간)은 4시간 창 안 운행만 대상.

## 4. 추천 이유(recommend_reason)와 등급(recommend_level)

각 추천 운행에는 추천 근거가 표시된다.

| reason | 근거 |
|---|---|
| `연결 운행` | 맡은 일정의 하차지 → 이어지는 다음 운행 |
| `매칭 설정` | 활성 매칭 설정 조건 일치 |
| `자주 다니는 노선` | 운행/요청 이력의 자주 다니는 지역 |
| `자주 운행한 시간` | 이력에서 자주 운행한 시간대 |

연결 운행은 `recommend_level`로 등급이 나뉜다.

| level | 의미 |
|---|---|
| `strong` | **공항 왕복(샌딩↔랜딩, 양방향)** 이며 하차지와 **같은 구** 또는 **같은 공항**(터미널·선 무관)에서 출발 → 홈 '강력추천' |

연결 운행은 항상 `strong`이다. (양방향 왕복 + 같은 구/같은 공항만 연결되므로)

## 5. 조건 일치율 점수 (match_score)와 근거 (match_reasons)

홈 추천·마켓 응답의 각 행에는 `match_score`(조건%)와 `match_reasons`(✓ 근거 체크리스트)가 붙는다. 구현: `app/Services/Order/OrderListService::matchProfile()`.

### 배점 구성 (합계 100, `min(100, 합계)`)

| 항목 | 배점 | 근거(✓) | 조건 |
|---|---|---|---|
| 매칭 설정 일치 | 25 | 매칭 설정에 맞는 운행 | 설정 조건이 실제 존재하고 일치 또는 앞·뒤 연결(`isMatch`/`isFrontLink`/`isBackLink`) |
| 차량 조건 | 20 | 차량 조건 일치 | 내 차량 종류와 운행 차량 부분 일치 |
| 지역 조건 | 20 | 선호 지역 운행 / 자주 다니는 노선 | 선호 지역(설정) 우선, 자주 다니는 지역(이력) 차선 |
| 시간대 조건 | 15 | 선호 시간대 운행 / 자주 운행한 시간대 | 선호 시간대(설정) 우선, 자주 운행한 시간(이력) 차선 |
| 금액 조건 | 10 | 최소 금액 이상 | `min_revenue` 설정이 있고 충족 |
| 동선·연결 | 10 | 현재 운행과 동선이 좋음 | 연결 운행 체인(`isChain`)에 포함 |

- **공항 운행**: 점수 없이 `공항 운행` 근거만 추가된다.
- 근거는 여러 항목이 충족되면 모두 쌓이고, 점수는 최대 100으로 제한된다.

### 최소 선호도 필터 (60% 미만 제외)

- 추천(`recommendations`)은 `config('recommendation.min_match_score')`(기본 **60**, env `RECOMMEND_MIN_MATCH_SCORE`) 미만이면 **추천에서 제외**한다.
- 예외: 셋트(`kind=set`)는 한 다리라도 매칭되면 셋트 전체 일정을 추천에 포함하므로 필터를 적용하지 않는다.
- 근거: 낮은 조건 일치율 후보로 기사의 판단 피로도를 늘리지 않기 위함 (제품 방향성: [PRODUCT_VISION.md](./PRODUCT_VISION.md)).
